# Qoima

SaaS для пищевых производителей и их точек продаж: заявки, остатки, отчёты смен и прогноз «сколько произвести завтра и сколько отправить в каждый магазин». Пилот — HAN Burger (Астана).

**Стек:** React 18 · TypeScript (strict) · Vite 6 · React Router · Zod · Supabase (Postgres + Auth + RLS + Realtime) · PWA · Vitest · Playwright · ESLint · Prettier · GitHub Actions · Vercel.

## Кабинеты и роли

| Роль                              | Что видит                                                                                                                              |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `owner` — владелец производства   | дашборд с прогнозом, задание в цех, план отгрузки, заявки, остатки, отчёты, магазины, продукция и цены, сотрудники, настройки компании |
| `manager` — менеджер производства | то же, кроме сотрудников и настроек компании                                                                                           |
| `store` — магазин                 | сводка, остатки своей точки, закрытие смены, новая заявка, доставка                                                                    |
| `superadmin` — платформа Qoima    | компании, тарифы и сроки оплаты, подключение клиента                                                                                   |

Права проверяются в базе (RLS + security definer функции), а не в интерфейсе: магазин физически не может прочитать данные чужой точки или чужой компании.

## Быстрый старт

```bash
npm ci
npx supabase start          # локальный Supabase в Docker, миграции применяются сами
cp .env.example .env.local  # подставьте API URL и anon key из `npx supabase status`
npm run dev                 # http://localhost:5173
```

1. Зарегистрируйтесь, создайте компанию и нажмите «Загрузить демо HAN Burger».
2. Суперадмина назначают вручную в SQL-редакторе:
   `update profiles set role = 'superadmin' where email = 'you@example.kz';`
3. Магазин: владелец приглашает email в «Сотрудники», сотрудник регистрируется с этим email и сразу попадает в кабинет своей точки.

### Облачный Supabase (для разработки/демо)

1. Создайте проект, выполните миграции: `npx supabase link --project-ref <ref>` и `npx supabase db push`.
2. Authentication → URL Configuration: добавьте адрес сайта в Site URL и Redirect URLs.
3. Для продакшена настройте свой SMTP (Authentication → SMTP): встроенный почтовик Supabase шлёт 2–4 письма в час.

## Архитектура

```
src/
  app/            провайдеры, авторизация, маршруты, каркас (меню, шапка)
  features/
    auth/         вход, регистрация с согласием на ПД, онбординг компании
    company/      загрузка данных компании + realtime, контекст
    forecast/     чистая модель прогноза (покрыта тестами)
    producer/     planning (дашборд, цех, отгрузка), operations (заявки, остатки, отчёты), directory (справочники)
    store/        кабинет магазина
    admin/        кабинет суперадмина
    account/      профиль, язык, удаление аккаунта
    legal/        политика обработки ПД
  shared/
    i18n/         ru / kk / en, типизированные ключи
    lib/          клиент Supabase, форматирование (₸, НДС 12%, БИН, телефон), zod-хелперы
    types/        сгенерированные типы БД и доменные типы
    ui/           компоненты, тосты, стили
supabase/
  migrations/     схема, RLS, RPC, согласие на ПД
  tests/          тесты RLS на PGlite
e2e/              сценарии Playwright
```

Правила:

- Все записи, которые меняют несколько таблиц (закрытие смены, заявка, смена статуса, выпуск продукции), идут через RPC-функции в одной транзакции. Клиент не пишет напрямую в остатки.
- Формы валидируются zod-схемами из `features/*/schemas.ts`; тексты ошибок — ключи i18n.
- Каждый экран обрабатывает загрузку, ошибку (с повтором) и пустое состояние.
- Типы БД генерируются, а не пишутся руками.

### Прогноз

- `нужно = ⌈ среднее за 7 дней (по дням, когда точка работала) × коэффициент дня недели × (1 + страховой запас) ⌉`
- `отправить = max(0, нужно − остаток в магазине − уже в открытых заявках)`
- `произвести = Σ отправить − остаток на складе`
- Коэффициент дня недели включается после 14 дней истории.
- Остаток «заканчивается», если его хватит меньше чем на полдня; «излишек», если больше чем на max(2, 0.8 × срок годности) дней.

## Качество

- **TypeScript strict** + `noUncheckedIndexedAccess`.
- **Тесты:** unit (форматирование, БИН, НДС, прогноз, схемы, полнота словарей kk/en, компоненты), RLS (изоляция компаний и магазинов, запрет смены роли, согласие, удаление аккаунта), e2e (полный сценарий владелец → магазин → отгрузка → получение → суперадмин, проверка согласия, мобильная вёрстка).
- **CI** (`.github/workflows/ci.yml`): типы, линт, формат, unit, RLS, сборка; затем e2e с поднятым Supabase.
- **Доступность:** семантические landmarks, ссылка «к содержимому», подписи у всех полей, `aria-invalid`/`aria-describedby` для ошибок, модалки с `role=dialog` и Escape, таблица-дубль для графиков, видимый фокус, `prefers-reduced-motion`.
- **Адаптив и PWA:** работает с телефона, устанавливается на главный экран. Данные не кэшируются офлайн, чтобы не показывать устаревшие остатки.

## Безопасность

- В коде нет секретов. На клиенте только публичный anon-ключ, доступ ограничен RLS. `service_role` ключ в приложении не используется.
- Мультиарендность: у всех таблиц `company_id`, составные внешние ключи `(id, company_id)` не дают связать запись с чужой компанией.
- Роль, компанию и магазин пользователь сам изменить не может (триггер `guard_profile`).
- `vercel.json`: CSP, HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`.

## Персональные данные (Закон РК № 94-V)

Сделано:

- согласие на сбор и обработку ПД при регистрации (сохраняются дата и версия политики; при новой версии пользователь подтверждает снова);
- страница политики `/privacy` (**шаблон, нужен юрист**: реквизиты оператора, сроки, порядок обращений);
- просмотр и исправление своих данных, отзыв согласия через удаление аккаунта; история продаж остаётся у компании без привязки к человеку.

**Важно — локализация данных (п. 2 ст. 12):** ПД граждан РК должны храниться в базе на территории Казахстана. У Supabase Cloud нет региона в РК, поэтому для продакшена:

- поднимите self-hosted Supabase (Docker) у казахстанского хостинга (PS Cloud, Kazakhtelecom, QazCloud и др.);
- примените те же миграции;
- укажите его адрес в `VITE_SUPABASE_URL` и в `connect-src` CSP в `vercel.json`.

Фронтенд на Vercel ПД не хранит. Облачный Supabase годится для разработки и демо без реальных сотрудников.

## Деплой на Vercel

1. Импортируйте репозиторий в Vercel (настройки берутся из `vercel.json`).
2. В Environment Variables добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
3. Добавьте домен Vercel в Redirect URLs Supabase Auth.

## Чего пока нет

- Оплаты (Kaspi Pay / эквайринг) — тарифы и `paid_till` суперадмин ведёт вручную.
- Отправки писем со своего домена — нужно настроить SMTP.
- Печатных форм накладных, интеграции с 1С и фискальными кассами.
- Мониторинга ошибок (Sentry) и аналитики — подключаются при выходе на платных клиентов.
